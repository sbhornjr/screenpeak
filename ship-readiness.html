App Router "special files"

In app/, certain filenames are wired up by Next.js automatically — you create the file, Next does the rest. The ones that matter here:

page.tsx
the UI for a route.
layout.tsx
shared shell wrapping a route and its children.
loading.tsx
shown instantly while page.tsx is fetching its data — Next wraps the segment in a React <Suspense> boundary for you.
error.tsx
catches errors thrown while rendering that segment and shows fallback UI. Must be a Client Component. You have this at the root.
not-found.tsx
rendered when notFound() is called or no route matches. You do not have this.
global-error.tsx
catches errors in the root layout itself. You have this.
route.ts
an API endpoint (exports GET, POST, …) instead of a page.
robots.ts / sitemap.ts / manifest.ts / icon.png / opengraph-image.png
each generates the matching file or <head> tag at build time.
proxy.ts
runs on the server before every matched request. In Next 16 this file was renamed from middleware.ts — yours is correct and working; don't rename it back.

Public vs secret environment variables

Anything named NEXT_PUBLIC_* is copied into the browser JavaScript bundle at build time. Any visitor can read it in devtools. That's fine for NEXT_PUBLIC_SUPABASE_URL and the anon key — they're designed to be public, and Row Level Security is what actually protects the data. Consequence: changing one of these needs a fresh build + redeploy.

Every other variable (SUPABASE_SECRET_KEY, ANTHROPIC_API_KEY, RAWG_API_KEY, STEAM_API_KEY) is only readable on the server — in Route Handlers, Server Components, and proxy.ts. Never prefix a secret with NEXT_PUBLIC_.

.env.local is your machine-only copy and is gitignored. .env.example is a committed copy with the same keys but blank values — it documents what the project needs.

Row Level Security (RLS)

A PostgreSQL feature Supabase is built on. Each table carries policies — small SQL rules evaluated per row that decide whether the current request may select / insert / update / delete that row. auth.uid() inside a policy returns the logged-in user's id.

This app sends every write straight from the browser to Supabase (see lib/queries/*). Those functions pass a row id and trust the database to refuse the write if the row isn't yours. So these policies are not a backstop — they are the only thing enforcing "you can only edit your own stuff." If a table has RLS off, or a policy that's too loose, any logged-in user can edit anyone's data by calling the same query with a different id.

How Supabase email links become a session

When a user clicks "confirm your email" or "reset your password" in an email, Supabase sends them to your app carrying a one-time credential — either ?code=… (the PKCE flow) or ?token_hash=…&type=… (the older flow). It never puts a real session token in an email; that would be a security hole.

supabase.auth.exchangeCodeForSession(code)
your server hands the code back to Supabase, which verifies it and returns real session cookies. Used for the PKCE ?code= links.
supabase.auth.verifyOtp({ type, token_hash })
the equivalent for ?token_hash=…&type=… links (type is signup, recovery, email_change, …).

Either way you need a route that receives the link and does the exchange, then redirects the user into the app. Without it, every email link dead-ends on a 404. That's item B3, and B2 depends on it.

What it is

app/user/[username]/loadout/page.tsx:66 runs generateLoadoutIdentity() — a paid Anthropic API call — on every render, whenever the profile has 5+ ratings. There's no caching, and no login is required: public loadouts render for anonymous visitors (lines 32–35). The call is also awaited inline, so it blocks the whole page for 1–3s each time.

Why it matters here

Separately: an AI-written "identity" that appears unbidden on every profile is an easy target for the anti-AI crowd — making it something the owner chooses to generate and can edit defuses both problems at once. (See also the product call: keep it opt-in and editable, skip the AI title.)

    export async function POST() {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return NextResponse.json({ error: 'unauthorized' }, { status: 401 })

  const { data: current } = await supabase
    .from('users').select('username, loadout_identity_at')
    .eq('id', user.id).single()
  if (!current?.username)
    return NextResponse.json({ error: 'no profile' }, { status: 400 })

  // one generation per minute, per user
  if (current.loadout_identity_at &&
      Date.now() - new Date(current.loadout_identity_at).getTime() < 60_000)
    return NextResponse.json({ error: 'slow down' }, { status: 429 })

  const input = await buildLoadoutInput(supabase, user.id, current.username)
  if (input.totalRatings < 5)
    return NextResponse.json({ error: 'not eligible' }, { status: 400 })

  const text = await generateLoadoutIdentity(input)
  if (!text) return NextResponse.json({ error: 'generation failed' }, { status: 502 })

  const { error } = await supabase.from('users')
    .update({ loadout_identity: text, loadout_identity_at: new Date().toISOString() })
    .eq('id', user.id)
  if (error) return NextResponse.json({ error: 'save failed' }, { status: 500 })

  return NextResponse.json({ text })
}

It maps 401/429/400 to inline messages shown full-width below the buttons. (Replaced the earlier separate GenerateLoadoutButton / SubmitBioButton pair, which misaligned.)

What generateMetadata is

An async function generateMetadata({ params }) you export from a page.tsx or layout.tsx. Next runs it on the server and uses the returned object to write the <title>, <meta name="description">, and the Open Graph / Twitter tags into <head>. Those OG tags are what Discord, iMessage, Slack, and Twitter read to build the preview card when someone pastes your link.

What metadataBase is

OG image URLs must be absolute (https://site.com/x.png, not /x.png). metadataBase: new URL('https://site.com') in the root layout tells Next what to prefix relative URLs with. Without it Next logs a build warning and falls back to http://localhost:3000, so every shared link's preview points at localhost.

Why it matters here

Right now only app/layout.tsx sets metadata, statically — so every page shares the title "NG+ | Your Gaming Identity". Your /games/[slug] and /user/[username] pages are exactly the ones people share, and they'd all preview identically with no game name and no cover art.

How to do it
  • In app/layout.tsx, extend the existing metadata: 
    export const metadata: Metadata = {

  description: 'Track, rate, and share the games that define you.',
  openGraph: { siteName: 'NG+', type: 'website' },
}
    The template means a page returning title: 'Hades' becomes "Hades | NG+" automatically.

Status — implemented & verified

Confirmed live via curl localhost:3000/robots.txt and /sitemap.xml — disallow list correct, sitemap carries real URLs and lastmod dates for games, users, and public lists.

What they are

app/robots.ts is served as /robots.txt — the first file every search-engine crawler fetches, telling it which paths it may crawl and where the sitemap is. app/sitemap.ts is served as /sitemap.xml — a supplementary hint listing URLs worth knowing about, not an access list. Crawlers mostly discover pages by following links (nav, game cards, "reviewed by X" links); the sitemap helps with pages that are harder to reach that way and signals lastModified for recrawling.

Why it matters here

Without them, search engines still crawl you — slowly, incompletely, and with no steer on what to index. robots.txt is advisory, not access control — it keeps well-behaved crawlers out of pages like /auth/update-password, which is still separately guarded by its own session check.

What was built
  • robots.ts disallows /settings, /steamlink, /auth/, /api/.
  • sitemap.ts includes: the three static pages; every game, ordered by metacritic_score desc nulls last before the 5000-row cap — without an explicit order Postgres returns rows in an unstable sequence, so ordering first means a cap (if it ever binds) drops the least-notable games, not an arbitrary slice; every user profile (there are no private profiles, so it's an unconditional include); and every list where is_public = true, joined back to its owner's username for the real /user/<username>/lists/<id> path.
  • Not filtered further by popularity — at this scale, "all public lists" is simpler and correct. Revisit with a sitemap index (multiple files) only if you ever approach Google's 50,000-URL-per-file limit.
Verify

What they are

HTTP response headers that instruct the browser to enforce specific protections. Next sets them for all routes via an async headers() function in next.config.ts (yours currently only configures images).

What each one does
  • Strict-Transport-Security (HSTS) — "only ever contact this site over HTTPS." Blocks downgrade attacks.
  • X-Frame-Options: DENY + Content-Security-Policy: frame-ancestors 'none' — "no other site may load this page in an <iframe>." Stops clickjacking, where an attacker frames your site invisibly over their own buttons to trick a logged-in user into clicking. Higher stakes for you because your whole auth flow is a modal.
  • X-Content-Type-Options: nosniff — "don't guess content types," so a file can't be served as an image and executed as script.
  • Referrer-Policy: strict-origin-when-cross-origin — don't leak full URLs (which can carry usernames/ids) to third-party sites.
  • Permissions-Policy — proactively switch off browser APIs you never use (camera, mic, geolocation).
How to do it 
// next.config.ts — add inside nextConfig
  async headers() {
    return [{
      source: '/:path*',
      headers: [
        { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
        { key: 'X-Frame-Options', value: 'DENY' },
        { key: 'X-Content-Type-Options', value: 'nosniff' },
        { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
        { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
        { key: 'Content-Security-Policy', value: "frame-ancestors 'none'" },
      ],
    }]
  },

A full Content-Security-Policy (restricting which script/style/image sources may load) is more involved because Next's inline scripts need a per-request nonce — reasonable to defer to v2. frame-ancestors alone is the high-value, low-risk piece.

Verify

curl -sI https://your-site | grep -i 'strict-transport\|x-frame', or run the URL through securityheaders.com.

What it is

Something that catches errors thrown on the server (ideally the client too) and sends them somewhere you'll actually see — a dashboard or a chat webhook — with the stack trace and which request caused it.

What instrumentation.ts + onRequestError are

instrumentation.ts is a Next file that runs once when the server process starts — the standard place to initialize a monitoring SDK. onRequestError is an optional function you export from it that Next calls on every unhandled server error, passing the error plus the route and request. That's the hook monitoring tools plug into.

Why it matters here

Your error.tsx and global-error.tsx currently only call logger.error(...), which in production goes to the browser console — nowhere you'll ever look. The first you'd hear of a broken page is a user telling you.

How to do it — pick one
  • Sentry (most complete): run npx @sentry/wizard@latest -i nextjs. It scaffolds instrumentation.ts, client/server config, and a source-map upload step. Free tier is generous. Then have error.tsx also call Sentry.captureException(error).

Defense-in-depth: Postgres CHECK constraints

These functions run client-side (browser components call them directly), so the zod layer is a shared source of truth + good UX, not a wall against someone bypassing your JS entirely. Run this once in the SQL editor for that layer — it checks for existing violations first, adds each constraint as not valid (so it doesn't fail immediately if data already exists), then only validates once you've confirmed there's nothing to fix:

-- 1. Check for existing violations before adding anything
select id, username from users where username !~ '^[A-Za-z0-9_]{3,20}$';
select id from users where char_length(coalesce(user_bio, '')) > 500;
select id from users where favorite_game_ids is not null and cardinality(favorite_game_ids) > 5;
select id, name from lists where char_length(name) not between 1 and 80;
select id from lists where char_length(coalesce(description, '')) > 500;
select user_id, game_id, rating from ratings_reviews where rating not between 1 and 10;
select user_id, game_id from ratings_reviews where char_length(coalesce(review, '')) > 5000;
-- Fix (or decide to grandfather) anything these return before continuing.

-- 2. Add the constraints without checking existing rows yet
alter table users add constraint username_format
  check (username ~ '^[A-Za-z0-9_]{3,20}$') not valid;
alter table users add constraint user_bio_length
  check (char_length(coalesce(user_bio, '')) <= 500) not valid;
alter table users add constraint favorite_games_max
  check (favorite_game_ids is null or cardinality(favorite_game_ids) <= 5) not valid;
alter table lists add constraint list_name_length
  check (char_length(name) between 1 and 80) not valid;
alter table lists add constraint list_description_length
  check (char_length(coalesce(description, '')) <= 500) not valid;
alter table ratings_reviews add constraint rating_range
  check (rating between 1 and 10) not valid;
alter table ratings_reviews add constraint review_length
  check (char_length(coalesce(review, '')) <= 5000) not valid;

-- 3. Only after step 1 comes back clean — validate for real
alter table users validate constraint username_format;
alter table users validate constraint user_bio_length;
alter table users validate constraint favorite_games_max;
alter table lists validate constraint list_name_length;
alter table lists validate constraint list_description_length;
alter table ratings_reviews validate constraint rating_range;
alter table ratings_reviews validate constraint review_length;

No constraint for selected_title — a DB CHECK can't express "one of this specific user's earned titles" any better than the zod layer can.

Key concept

NEXT_PUBLIC_* values are baked into the JS bundle at build time — change one later and you must redeploy for it to take effect. Secret vars are read at runtime on the server, so rotating one only needs a redeploy, no code change.
