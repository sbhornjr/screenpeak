App Router "special files"

In app/, certain filenames are wired up by Next.js automatically — you create the file, Next does the rest. The ones that matter here:

page.tsx
the UI for a route.
layout.tsx
shared shell wrapping a route and its children.
loading.tsx
shown instantly while page.tsx is fetching its data — Next wraps the segment in a React <Suspense> boundary for you.
error.tsx
catches errors thrown while rendering that segment and shows fallback UI. Must be a Client Component. You have this at the root.
not-found.tsx
rendered when notFound() is called or no route matches. You do not have this.
global-error.tsx
catches errors in the root layout itself. You have this.
route.ts
an API endpoint (exports GET, POST, …) instead of a page.
robots.ts / sitemap.ts / manifest.ts / icon.png / opengraph-image.png
each generates the matching file or <head> tag at build time.
proxy.ts
runs on the server before every matched request. In Next 16 this file was renamed from middleware.ts — yours is correct and working; don't rename it back.

Public vs secret environment variables

Anything named NEXT_PUBLIC_* is copied into the browser JavaScript bundle at build time. Any visitor can read it in devtools. That's fine for NEXT_PUBLIC_SUPABASE_URL and the anon key — they're designed to be public, and Row Level Security is what actually protects the data. Consequence: changing one of these needs a fresh build + redeploy.

Every other variable (SUPABASE_SECRET_KEY, ANTHROPIC_API_KEY, RAWG_API_KEY, STEAM_API_KEY) is only readable on the server — in Route Handlers, Server Components, and proxy.ts. Never prefix a secret with NEXT_PUBLIC_.

.env.local is your machine-only copy and is gitignored. .env.example is a committed copy with the same keys but blank values — it documents what the project needs.

Row Level Security (RLS)

A PostgreSQL feature Supabase is built on. Each table carries policies — small SQL rules evaluated per row that decide whether the current request may select / insert / update / delete that row. auth.uid() inside a policy returns the logged-in user's id.

This app sends every write straight from the browser to Supabase (see lib/queries/*). Those functions pass a row id and trust the database to refuse the write if the row isn't yours. So these policies are not a backstop — they are the only thing enforcing "you can only edit your own stuff." If a table has RLS off, or a policy that's too loose, any logged-in user can edit anyone's data by calling the same query with a different id.

How Supabase email links become a session

When a user clicks "confirm your email" or "reset your password" in an email, Supabase sends them to your app carrying a one-time credential — either ?code=… (the PKCE flow) or ?token_hash=…&type=… (the older flow). It never puts a real session token in an email; that would be a security hole.

supabase.auth.exchangeCodeForSession(code)
your server hands the code back to Supabase, which verifies it and returns real session cookies. Used for the PKCE ?code= links.
supabase.auth.verifyOtp({ type, token_hash })
the equivalent for ?token_hash=…&type=… links (type is signup, recovery, email_change, …).

Either way you need a route that receives the link and does the exchange, then redirects the user into the app. Without it, every email link dead-ends on a 404. That's item B3, and B2 depends on it.

What it is

app/user/[username]/loadout/page.tsx:66 runs generateLoadoutIdentity() — a paid Anthropic API call — on every render, whenever the profile has 5+ ratings. There's no caching, and no login is required: public loadouts render for anonymous visitors (lines 32–35). The call is also awaited inline, so it blocks the whole page for 1–3s each time.

Why it matters here

Every page load is one Sonnet call you pay for, and one bot crawling public profiles runs up an unbounded bill. Separately: an AI-written "identity" that appears unbidden on every profile is an easy target for the anti-AI crowd — making it something the owner chooses to generate and can edit defuses both problems at once. (See also the product call: keep it opt-in and editable, skip the AI title.)

  • app/api/loadout/route.ts — no body. The caller is identified by session; username and stats are read server-side so they can't be spoofed: 
    export async function POST() {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return NextResponse.json({ error: 'unauthorized' }, { status: 401 })

  const { data: current } = await supabase
    .from('users').select('username, loadout_identity_at')
    .eq('id', user.id).single()
  if (!current?.username)
    return NextResponse.json({ error: 'no profile' }, { status: 400 })

  // one generation per minute, per user
  if (current.loadout_identity_at &&
      Date.now() - new Date(current.loadout_identity_at).getTime() < 60_000)
    return NextResponse.json({ error: 'slow down' }, { status: 429 })

  const input = await buildLoadoutInput(supabase, user.id, current.username)
  if (input.totalRatings < 5)
    return NextResponse.json({ error: 'not eligible' }, { status: 400 })

  const text = await generateLoadoutIdentity(input)
  if (!text) return NextResponse.json({ error: 'generation failed' }, { status: 502 })

  const { error } = await supabase.from('users')
    .update({ loadout_identity: text, loadout_identity_at: new Date().toISOString() })
    .eq('id', user.id)
  if (error) return NextResponse.json({ error: 'save failed' }, { status: 500 })

  return NextResponse.json({ text })
}

The component body stays sync; the onClick handlers are async — that's the part that awaits. It maps 401/429/400 to inline messages shown full-width below the buttons. (Replaced the earlier separate GenerateLoadoutButton / SubmitBioButton pair, which misaligned.)
  • In page.tsx, the Read-out card renders <LoadoutActions userId={ownerId.id} identity={loadoutIdentity} /> only when isOwner — passing identity="" in the "not generated yet" state hides the Save button — plus a quiet drafted with AI · edit anytime line.

What it is

A Route Handler at app/auth/callback/route.ts that receives the credential from Supabase email links (?code= or ?token_hash=&type=), exchanges it for a real session, and redirects the user into the app. See the concept "How Supabase email links become a session".

Why it matters here

Every email flow — signup confirmation, password reset (B2), email-change confirmation (you already have updateEmail at user.ts:137) — sends the user to a link pointing back at your app. With no route to catch it, the link 404s and the flow dies.

How to do it 
// app/auth/callback/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { createClient } from '@/lib/supabase-server'

export async function GET(request: NextRequest) {
  const { searchParams, origin } = request.nextUrl
  const next = searchParams.get('next') ?? '/'
  const code = searchParams.get('code')
  const token_hash = searchParams.get('token_hash')
  const type = searchParams.get('type') as
    'signup' | 'recovery' | 'email_change' | 'invite' | 'magiclink' | null

  const supabase = await createClient()
  let error = null

  if (code) {
    ({ error } = await supabase.auth.exchangeCodeForSession(code))
  } else if (token_hash && type) {
    ({ error } = await supabase.auth.verifyOtp({ type, token_hash }))
  } else {
    error = new Error('missing code')
  }

  if (error) {
    return NextResponse.redirect(`${origin}/?auth_error=1`)
  }
  return NextResponse.redirect(`${origin}${next}`)
}

Then, in the Supabase dashboard:

  • Authentication → URL Configuration: set "Site URL" to your production URL; add https://your-site/auth/callback to "Redirect URLs".
  • Authentication → Email Templates: the default templates link to {{ .SiteURL }}/auth/confirm?token_hash=…&type=…. Either change them to /auth/callback, or also create app/auth/confirm/route.ts with the same body — the handler above already covers both shapes, so pointing the templates at /auth/callback is simplest.
  • Authentication → Providers → Email: decide whether "Confirm email" is on (recommended). If on, this route is mandatory for signup to work at all.
Verify

Fresh signup → confirmation email → click the link → you land logged-in on the app, not on a 404.

What it is

Confirming that every table in Supabase has Row Level Security enabled and policies that tie writes to the logged-in user. See the RLS concept.

Why it matters here

All writes go browser → Supabase directly. updateList(listId, …), setListPinned(listId, …), syncListGames(listId, …), removeGameFromList(listId, gameId) in lib/queries/list.ts send only a list id — they trust the database to reject the write if that list isn't yours. If RLS is missing or permissive on any user-owned table, anyone logged in can edit or delete anyone's lists, ratings, library, or profile.

How to do it
  • Supabase dashboard → Database → Tables. For every user-owned table (lists, list_games, ratings/reviews, library, account_settings/profiles, follows, …): confirm the "RLS enabled" toggle is on and there is a policy for each operation you perform.
  • The pattern for rows owned by a user: 
    -- read: your own rows, plus public ones
create policy "read own or public" on lists
  for select using (is_public or auth.uid() = user_id);

-- writes: only your own
create policy "insert own" on lists
  for insert with check (auth.uid() = user_id);
create policy "update own" on lists
  for update using (auth.uid() = user_id)
             with check (auth.uid() = user_id);
create policy "delete own" on lists
  for delete using (auth.uid() = user_id);
  • For a join/child table like list_games, the check hops through the parent: 
    create policy "write via owned list" on list_games
  for all using (exists (
    select 1 from lists
    where lists.id = list_games.list_id
      and lists.user_id = auth.uid()
  ));
  • Don't forget storage.objects for the avatar/image bucket — same thinking: public select, writes scoped to the user's own folder.
Verify

With two accounts: log in as A, take a list_id belonging to B (visible on B's public profile), and in the browser console run the same .update() your app runs against it. It must return zero rows / an error — not succeed. Repeat the idea for each user-owned table.

What generateMetadata is

An async function generateMetadata({ params }) you export from a page.tsx or layout.tsx. Next runs it on the server and uses the returned object to write the <title>, <meta name="description">, and the Open Graph / Twitter tags into <head>. Those OG tags are what Discord, iMessage, Slack, and Twitter read to build the preview card when someone pastes your link.

What metadataBase is

OG image URLs must be absolute (https://site.com/x.png, not /x.png). metadataBase: new URL('https://site.com') in the root layout tells Next what to prefix relative URLs with. Without it Next logs a build warning and falls back to http://localhost:3000, so every shared link's preview points at localhost.

Why it matters here

Right now only app/layout.tsx sets metadata, statically — so every page shares the title "NG+ | Your Gaming Identity". Your /games/[slug] and /user/[username] pages are exactly the ones people share, and they'd all preview identically with no game name and no cover art.

How to do it
  • In app/layout.tsx, extend the existing metadata: 
    export const metadata: Metadata = {
  metadataBase: new URL(process.env.NEXT_PUBLIC_SITE_URL ?? 'http://localhost:3000'),
  title: { default: 'NG+ | Your Gaming Identity', template: '%s | NG+' },
  description: 'Track, rate, and share the games that define you.',
  openGraph: { siteName: 'NG+', type: 'website' },
}
    The template means a page returning title: 'Hades' becomes "Hades | NG+" automatically.
  • In app/games/[slug]/page.tsx, add alongside the default export: 
    export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> }
): Promise<Metadata> {
  const { slug } = await params
  const supabase = await createClient()
  const game = await getGameBySlug(supabase, slug)   // your existing query
  if (!game) return {}
  return {
    title: game.name,
    description: game.description_short
      ?? `Ratings and reviews for ${game.name} on NG+.`,
    openGraph: {
      title: game.name,
      images: game.cover_image_url ? [game.cover_image_url] : [],
    },
  }
}
  • Same shape for app/user/[username]/page.tsx — title: `${username}`, description from the bio.
  • Add NEXT_PUBLIC_SITE_URL to .env.local and (later) the host. Next dedupes the query between generateMetadata and the page within one request, so you're not paying for it twice.
Verify

curl -s https://your-site/games/<slug> | grep -i 'og:title\|<title>' shows the game name. Paste the link into Discord → the card shows the cover.

What they are

app/robots.ts is served as /robots.txt — the first file every search-engine crawler fetches, telling it which paths it may crawl and where the sitemap is. app/sitemap.ts is served as /sitemap.xml — a machine-readable list of every URL you want indexed, so crawlers find pages they might not reach by following links (every game detail page, say).

Why it matters here

Without them, search engines still crawl you — slowly, incompletely, and with no steer on what to index (you probably don't want /settings or /steamlink in Google). For a public-profile app, being findable is part of the point.

How to do it 
// app/robots.ts
import type { MetadataRoute } from 'next'

export default function robots(): MetadataRoute.Robots {
  const base = process.env.NEXT_PUBLIC_SITE_URL ?? 'http://localhost:3000'
  return {
    rules: { userAgent: '*', allow: '/', disallow: ['/settings', '/steamlink', '/api/'] },
    sitemap: `${base}/sitemap.xml`,
  }
}
// app/sitemap.ts
import type { MetadataRoute } from 'next'
import { createClient } from '@/lib/supabase-server'

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const base = process.env.NEXT_PUBLIC_SITE_URL ?? 'http://localhost:3000'
  const supabase = await createClient()
  const { data: games } = await supabase
    .from('games').select('slug, updated_at').limit(5000)

  return [
    { url: base, lastModified: new Date() },
    { url: `${base}/games`, lastModified: new Date() },
    { url: `${base}/explore`, lastModified: new Date() },
    ...(games ?? []).map((g) => ({
      url: `${base}/games/${g.slug}`,
      lastModified: g.updated_at ? new Date(g.updated_at) : undefined,
    })),
  ]
}

You can append public user profiles too — but only rows where the user set their profile public.

Visit /robots.txt and /sitemap.xml on the deployed site; the sitemap lists your game URLs.

What they are

HTTP response headers that instruct the browser to enforce specific protections. Next sets them for all routes via an async headers() function in next.config.ts (yours currently only configures images).

What each one does
  • Strict-Transport-Security (HSTS) — "only ever contact this site over HTTPS." Blocks downgrade attacks.
  • X-Frame-Options: DENY + Content-Security-Policy: frame-ancestors 'none' — "no other site may load this page in an <iframe>." Stops clickjacking, where an attacker frames your site invisibly over their own buttons to trick a logged-in user into clicking. Higher stakes for you because your whole auth flow is a modal.
  • X-Content-Type-Options: nosniff — "don't guess content types," so a file can't be served as an image and executed as script.
  • Referrer-Policy: strict-origin-when-cross-origin — don't leak full URLs (which can carry usernames/ids) to third-party sites.
  • Permissions-Policy — proactively switch off browser APIs you never use (camera, mic, geolocation).
How to do it 
// next.config.ts — add inside nextConfig
  async headers() {
    return [{
      source: '/:path*',
      headers: [
        { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
        { key: 'X-Frame-Options', value: 'DENY' },
        { key: 'X-Content-Type-Options', value: 'nosniff' },
        { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
        { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
        { key: 'Content-Security-Policy', value: "frame-ancestors 'none'" },
      ],
    }]
  },

A full Content-Security-Policy (restricting which script/style/image sources may load) is more involved because Next's inline scripts need a per-request nonce — reasonable to defer to v2. frame-ancestors alone is the high-value, low-risk piece.

Verify

curl -sI https://your-site | grep -i 'strict-transport\|x-frame', or run the URL through securityheaders.com.

What it is

Something that catches errors thrown on the server (ideally the client too) and sends them somewhere you'll actually see — a dashboard or a chat webhook — with the stack trace and which request caused it.

What instrumentation.ts + onRequestError are

instrumentation.ts is a Next file that runs once when the server process starts — the standard place to initialize a monitoring SDK. onRequestError is an optional function you export from it that Next calls on every unhandled server error, passing the error plus the route and request. That's the hook monitoring tools plug into.

Why it matters here

Your error.tsx and global-error.tsx currently only call logger.error(...), which in production goes to the browser console — nowhere you'll ever look. The first you'd hear of a broken page is a user telling you.

How to do it — pick one
  • Sentry (most complete): run npx @sentry/wizard@latest -i nextjs. It scaffolds instrumentation.ts, client/server config, and a source-map upload step. Free tier is generous. Then have error.tsx also call Sentry.captureException(error).
  • Minimal, no dependency: 
    // instrumentation.ts
export async function onRequestError(err: unknown, request: { path: string }) {
  await fetch(process.env.ERROR_WEBHOOK_URL!, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({
      content: `⚠️ ${request.path}\n${err instanceof Error ? err.stack : String(err)}`,
    }),
  })
}
    Point ERROR_WEBHOOK_URL at a Discord or Slack incoming webhook.
Verify

Deploy, temporarily add a route that throws, hit it, confirm the error lands in Sentry / your webhook, then remove the throw.

What it is

Checking that form data is well-formed on the server — in your lib/queries/* functions — before it reaches the database: length limits, required fields, allowed characters.

Why it matters here

Client checks (AuthModal password length, AvatarUploader file size) are bypassable — anyone can call your Supabase endpoints directly. Concretely: the review textarea has no max length, so one review can insert megabytes of text; usernames have no format/length rules and DB errors are swallowed (ChangeUsernameButton ignores the return value); bio is unbounded.

How to do it

Add a schema library — npm i zod — and validate at the top of each write function:

import { z } from 'zod'

const reviewSchema = z.object({
  gameId: z.string().uuid(),
  rating: z.number().int().min(1).max(10),
  body: z.string().max(5000).optional(),
})

export async function upsertReview(supabase, input: unknown) {
  const parsed = reviewSchema.safeParse(input)
  if (!parsed.success) {
    return { error: parsed.error.issues[0].message }
  }
  const { gameId, rating, body } = parsed.data
  // ...write
}
  • .parse() throws on bad input; .safeParse() returns { success, data | error } so you can show a message. Use safeParse at boundaries.
  • Priorities: review body max(5000); username z.string().min(3).max(20).regex(/^[a-z0-9_]+$/i); bio max(500); list name required + max(80).
  • Stop swallowing errors — return { error } to the component so a failed change tells the user instead of silently doing nothing.
Verify

From the UI, try to save a too-long username and an oversized review → clean error message, no DB write.

What it is

A /privacy page describing what personal data you collect and why, a /terms page with the usage rules, and a checkbox at signup where the user agrees to both.

Why it matters here

You collect email, uploaded avatars, free-text reviews, and the user's entire Steam owned-games library + Steam ID, and you send profile data to Anthropic (a third-party "processor"). In most jurisdictions that triggers a disclosure obligation; app stores and some payment providers also require a public privacy policy to exist. The Steam import in particular raises what users reasonably expect to be told.

D0 · Pick a host

For a Next.js 16 app the path of least resistance is Vercel — the company that makes Next.js. Zero config, it understands the proxy.ts edge runtime, every git push gets its own preview URL, and the free "Hobby" tier covers a project at this stage.

Alternatives, roughly in order of "more control, more setup": Netlify (very similar to Vercel) · Railway / Render / Fly.io (you run it as a Node server) · a VPS running npm run build && npm run start behind nginx. The rest of this runbook assumes Vercel, but the concepts — env vars, Supabase URL config, the build check — are identical everywhere.

Do this

Do this

Project → Settings → Environment Variables. Add each key from your .env.local, ticking "Production" (and "Preview" if you want preview deploys to work):

  • NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY — public; safe here, they're in the browser bundle by design.
  • NEXT_PUBLIC_SITE_URL — your production URL, e.g. https://ngplus.vercel.app (or your custom domain). Used by metadataBase (S3), robots.ts/sitemap.ts (S4), and the auth redirectTo (B2).
  • SUPABASE_SECRET_KEY, ANTHROPIC_API_KEY, RAWG_API_KEY, STEAM_API_KEY — secret; server-only, never prefixed NEXT_PUBLIC.
Key concept

NEXT_PUBLIC_* values are baked into the JS bundle at build time — change one later and you must redeploy for it to take effect. Secret vars are read at runtime on the server, so rotating one only needs a redeploy, no code change.
